# Files and Folders — agent orientation

D9/D10 custom file manager. On-disk dir `filesandfolders`; real machine name `files_and_folders`. Node-based (`folder`/`file` bundles) with parent-folder refs, role-based access via `field_authorized_roles`, and many AJAX routes in `files_and_folders.routing.yml` -> `src/Controller/FileFolderController.php`.

## Verified security findings

- **D3/D4 — Unrestricted file upload (RCE-adjacent / stored XSS).** `FileFolderController::uploadFiles()` (files_and_folders.routing.yml route `files_and_folders.upload_files`, permission only `access content` — granted to anonymous by default). The uploaded file keeps its client-supplied name/MIME and is written to `public://files_and_folders/` with **no extension allowlist / no `file_validate_extensions`**. An attacker with 'access content' (potentially anonymous) can upload `.html`/`.svg` (stored XSS) or server-side scripts; script execution is only mitigated by Drupal core's default `.htaccess` in the files dir. Also does not verify the target folder's authorized roles. Fix: enforce an extension allowlist via `file_validate_extensions`/`file_save_upload`, tighten the route permission, and check parent-folder access.
- **D3 — Role-restricted file disclosure via download.** `FileFolderController::downloadFile()` (route `files_and_folders.download_file`, permission `access content`) loads the `file` node, checks only `$node->access('view')` (standard published-node access), then streams the raw URI via `BinaryFileResponse` — ignoring the folder-role model (`checkFolderAccess`/`field_authorized_roles`) enforced by the listing endpoints, and bypassing private-scheme file access. Any user with 'access content' (incl. anonymous) can download any file node by iterating `{fileId}` regardless of the role-restricted folder it lives in. Fix: apply the folder authorized-roles check and use proper private-file access control.
- **Lower severity:** most mutation endpoints (`createFolder`, `createRootFolder`, `updateItemName`, `moveItem`, `deleteItem`, layout/icon settings) are gated only by `access content`; update/move/delete do call `$node->access(...)`, but create/root-folder creation and settings writes are effectively open to any 'access content' user. `field_visibility`/authorized roles are attacker-supplied on create.

Note: the access model relies on `field_authorized_roles` intersection with the user's roles; folder-listing queries use `accessCheck(FALSE)` and filter in PHP, so the download/upload gaps above are the real exposure.
