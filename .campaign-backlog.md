## Version-selection rule (decided wave 2)
`composer require drupal/x` resolves to the highest *stable* release, which can be an
older, D9-only major when the D11-compatible one is a pre-release of a higher major.
Caught by `scripts/check-major.sh`. media_directories hit this: stable 2.0.2 is
`^8.8.3 || ^9`; we moved it to 3.0.0-beta1 (`^10.2 || ^11 || ^12`).

Rule applied: take the highest major that has a real tagged release supporting D11.
Do NOT downgrade a working stable D11 release to an alpha/dev of a higher major, and
ignore majors that exist only as dev branches. Wave-1 audit flagged three projects under
this rule and all three were correctly left alone:
  - config_override_warn 1.5.0 — 2.x is dev-branch only
  - block_classes 1.0.4      — 2.0.x is dev-branch only
  - views_entity_form_field 1.2.0 (stable, ^10.1||^11) — 2.x is only 2.0.0-alpha1

Note `drush en` is itself a D11 compatibility gate: a module that enables is D11-compatible,
so wave-prepare.sh's FAILED column catches the incompatible-major case automatically.

## Site repair (during wave 2): missing default config
An over-broad `field_purge_batch()` sweep by a wave-1 agent destroyed field storages
belonging to modules it did not own. Nine enabled modules were left without their shipped
`config/install` defaults, and critically `domain_source`/`domain_access` lost
`field.storage.node.field_domain_*`, which made `NodeType::create()->save()` throw
site-wide — no agent could create a content type, a very common eval pattern.

Repaired with `scripts/check-default-config.sh --fix` (calls
`config.installer->installDefaultConfig()` per module): acquia_search, cas, domain_access,
domain_source, fontawesome, fontawesome_menu_icons, media_entity_instagram, realname,
section_library. Verified afterwards: ALL-DEFAULT-CONFIG-PRESENT, and node-type
create/delete works again.

Run this audit at the close of every wave — a module can sit in core.extension looking
Enabled while its default config is absent, which silently invalidates any doc or eval
written against it. The agent brief now forbids unscoped field purges.

### Durable fix for the recurring domain field purge
Reinstalling `domain_*` default config was not enough: the storages ship
`persist_with_no_fields: false`, and with no node bundle actually holding an instance, the
next content-type deletion by any agent purged them again — breaking `NodeType::create()`
site-wide a second time within the same wave.

Durable repair: reinstall the storages, then call the modules' own helpers
`domain_access_confirm_fields("node", $bundle)` and `domain_source_confirm_fields("node",
$bundle)` for every existing node bundle. The storages now hold instances on all permanent
bundles (article, page, ...), so deleting a temporary eval bundle can no longer orphan
them. Verified: create/delete a probe content type, storages still present.

`wave-prepare.sh` now runs `check-default-config.sh --fix` automatically after enabling,
so later waves repair this class of damage before agents ever see it.
